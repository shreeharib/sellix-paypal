Sellix Agent Harness

How the sellix backend answers a shop's Instagram DMs: the webhook that receives a customer's first message, the job that starts a turn, the engine that runs the model with tools, and the playbooks, memory, state and checks around it, up to the reply leaving through the outbox. Everything on this page was read from the code. Project status comes from the team's handoff notes.

§1

The short version

The model chooses tools and writes words. Code owns everything that can cost money or trust: which tools exist right now, every price, total and link, every change of state, whether a "yes" places an order, and whether a reply may be sent at all.

A tool-calling loop, built in-house

engine.py calls the model with the tools the chat's stage allows, runs the tool calls it returns, feeds the results back, and stops when send_reply passes the output checks. There is no agent framework.

A state machine gates the tools

Each chat is in one of five stages (conversations.order_stage). Only tools move it, and the model only sees the tools its stage allows: confirm_order does not exist until create_quote has queued a quote card.

Code picks the playbook

Ordered regex rules on the stage and the latest message pick one of 11 playbooks per turn. The playbook is a markdown prompt added to the system prompt, the project's version of a "skill".

Tokens instead of facts

The model writes [[price:i3f9a2c]], [[quote_total]], [[payment_link]]. Code fills them from the database when the reply is sent, and rejects any amount, link or item id the model typed itself.

Durable from webhook to send

A webhook inbox, a job queue in Postgres, a trace row for every turn and every step, and an outbox. A crashed turn resumes from its stored steps without placing an order or sending a message twice.

Never silent, owner in the loop

When a turn can't finish, code sends a fixed message and asks the shop owner. The owner's answer comes back as a shop event that starts a new turn, which passes it on in the customer's language.

Three things start a turn

Every turn answers one row in the messages table, called the trigger. Three kinds of row can be a trigger, and all three take the same path into the engine.

sender = customer

A customer message

A DM, a story reply, a photo, or a tap on a button (Confirm, Change, New payment link, a choice).

sender = system · event

A shop event

Payment received, paid after items sold out, hold expired. Written by code as a system note with the event as data.

event = owner_answered

The owner's answer

The shop owner answered an "Ask me" question in the app. It becomes a system note and gets its own playbook.

§3

Architecture

Two processes, one database

  • API (FastAPI, app/main.py): webhooks, the merchant app's /v1 API, the simulator. It loads and checks every prompt file at start-up, so a broken prompt stops the app instead of a customer's turn.
  • Worker (procrastinate, python -m app.worker): runs every job. In development it runs inside the API process (RUN_WORKER_IN_PROCESS=true); deployed, it is its own service.
  • Postgres is the database, the job queue, the lock server (advisory locks) and the trace store. No Redis, no workflow engine.

Module boundaries

  • Each module under app/modules/ exposes service.py and schemas.py; other modules import only those. A unit test enforces the rule.
  • The agent reaches orders, stock, the catalogue, payments, escalations and conversations through their services. It never writes another module's tables directly.
  • Jobs are queued only after the transaction that created their data has committed, because the queue uses its own connections. A reconciler catches the rare lost enqueue.
§4

The first message, step by step

A new customer writes to the shop: "Hi! Can I get 2 chocolate cookies for pickup this evening?" These are the steps the code takes, in order. Teal steps are code; the amber step is where the model works.

  1. Instagram delivers the webhook

    The route checks X-Hub-Signature-256 (HMAC-SHA256 of the raw body with the app secret), stores the raw event in webhook_events with dedupe_key = sha256(body) and ON CONFLICT DO NOTHING, commits, queues process_meta_event, and answers 200 at once. If storing fails it answers an error, so Meta delivers again.

    app/webhooks/meta.py · receive_event · service.record_event

  2. A worker claims the event and stores the message

    The job locks the event row (FOR UPDATE SKIP LOCKED, status pending), parses Meta's payload into channel-neutral messages and calls handle_incoming for each. It retries up to 5 times with exponential waits.

    app/webhooks/tasks.py · process_meta_event

  3. handle_incoming files the message under one chat

    • Finds the shop by its Instagram account id, upserts the customer, and gets or creates the one conversation for that customer (locked for the rest of the transaction).
    • An echo of the shop's own message is matched against the outbox. If the owner typed it in the Instagram app, the agent steps back from this chat (agent_paused_reason = merchant_replied).
    • Inserts the message (unique on shop and Instagram message id, so a redelivered webhook stores nothing), sets last_customer_message_at (this opens Instagram's 24-hour reply window), and releases outbox rows and owner answers that were waiting for the window.
    • More than 20 customer messages in 5 minutes counts as a burst: the message is stored but starts no turn.
    app/modules/conversations/service.py · handle_incoming

  4. A turn is requested, 3 seconds later, one per chat

    After the commit, request_turn reads the shop's agent_engine and queues run_agent_turn_v2 with three settings: schedule_in 3 s, queueing_lock = turn:<chat> (a second message inside those 3 s queues nothing; the waiting turn will see it) and lock = conversation:<chat> (turns of one chat never run side by side). The job gets up to 3 attempts, 5 s apart.

    app/modules/conversations/tasks.py · request_turn

  5. The engine takes the chat's lock

    A Postgres advisory lock on ("agent_turn", chat id), waiting up to 90 s for a running copy to finish. This guards against a redelivered job, the reconciler or the simulator starting a second copy. Busy after 90 s: return, and the reconciler tries again.

    agent/engine.py · run_turn · core/locks.py

  6. Everything the turn reads, in one transaction

    Stage and draft, the shop, the last 20 messages (in causal order), the trigger, the business date, the 24-hour window, today's stock, the next 14 days' stock, the shop profile, the open quote, this chat's unpaid order numbers, open owner questions, the customer's remembered facts, the owner's saved answers, the glossary, and the latest summary.

    agent/engine.py · _gather

  7. Start the trace, or find this turn already done

    agent_turns is unique on (conversation_id, trigger_message_id). A new row means a new turn. A finished row means the message was already answered: stop. A running row means an earlier attempt crashed: load its stored steps and resume.

    agent/tracing.py · start

  8. Pick the playbook and build the prompt

    choose_playbook("browsing", "Hi! Can I get 2 chocolate cookies…") matches no special rule and falls through to new_order. The system prompt is base.md + playbook.new_order + context.md filled with the gathered data; the chat follows as user and assistant messages (§6).

    agent/context.py · choose_playbook · build

  9. The inbound gate

    No model call if the message is over 4,000 characters, the chat has used its turns for the hour or day, or the shop's daily AI budget is spent. Each sends a fixed template instead (§10).

    agent/guardrails/inbound.py · check

  10. The loop: the model calls tools until a reply is accepted

    First, a tapped button is handled by code (none here). Then the model gets the messages and the 16 tools allowed in browsing. Each response's tool calls run in order; each result goes back as a tool message. The tool list is recomputed before every model call, so after create_quote moves the chat to awaiting_confirmation the model sees confirm_order and no longer sees create_quote. The trace below shows a typical run.

    agent/engine.py · _loop · _model_step · _tool_step

  11. Finish the trace

    The turn row gets its status (replied), the stage after, the playbook, every prompt version used, the models, token counts, cost and latency.

    agent/tracing.py · finish

  12. Deliver the outbox

    The quote card and the reply go out in queue order, at least 1 s apart. When the card is delivered, the outbox marks the quote as shown; only then can it be confirmed.

    conversations/outbox.py · deliver · _after_delivery

The card is the real quote_card@2 template rendered by prompt_store.text; the price is an example. The card is written by code, so the model never types the total.

When the customer taps Confirm

The tap arrives as a message whose payload is CONFIRM:<quote id>. Before any model call, _apply_tap ("layer 0") runs confirm() in code: the card must have been delivered before this message, the quote must be open and unexpired, the customer may not already have 2 unpaid orders, and the price must not have changed. The order is placed, stock is held for 15 minutes, the stage becomes payment_pending, and code queues the payment message.

The engine then appends the tap as a synthetic confirm_order call and its result, so the model only has to write a one-line thank-you.

§5

Choosing a playbook

A playbook is a short markdown prompt for one situation (taking an order, a payment question, the owner's answer). It sits between base.md and the context block in the system prompt. Exactly one is chosen per turn, by code, before the model is called.

choose_playbook(stage, text, details) reads three inputs: the chat's stage, the text of the latest customer message, and the trigger's details (an event, a story reply, attachments). The rules run in this order and the first match wins.

Switching mid-turn

The model can call load_playbook(name) once per turn when the conversation clearly moved to another situation. The playbook's text comes back as the tool result. Nine playbooks can be loaded this way; menu and owner_answer are left out of the tool's list, so they can only be chosen by the router.

Why regex, not a classifier

A recorded team decision (HANDOFF §5): cheap, fast, deterministic and unit-tested. The planned next step, if traces show misrouting, is a small classifier model. One routing gap found while writing this page: "what else do you have" never reaches menu. The menu rule matches "anything else" and "what do you have" but not "what else", so in browsing it falls through to new_order, and while paying it goes to payment_problem.

§6

The next message: keeping the conversation's context

Nothing is kept in the worker's memory between turns. Every turn rebuilds the whole prompt from Postgres, so any worker can run any turn, and a restart loses nothing. The conversation's context is the stored chat plus the stored state, rendered fresh each time.

What the model receives in one call

system · base@4

Who the agent is, how it works (tools only, every turn ends with send_reply), 7 hard rules, voice and style. Kept short and first, so the provider can cache the stable start of the prompt.

system · playbook

The one playbook the router chose.

system · context@5

The shop's profile, the owner's saved answers, the glossary, the shop's local time, today's menu (name, item id, price token, count left), facts about this customer, pre-orders coming up, the stage, the draft, the open quote and whether its card was delivered, unpaid order numbers, questions waiting on the owner, a closing-window warning, and the summary of older messages.

user

Each customer message: normalised (NFKC, invisible characters removed), at most 1,000 characters, and the latest burst at most 2,000 characters in all, oldest cut first. A story reply or attachment gets a short marker.

assistant

Our earlier replies, and messages the owner typed in Instagram as (Shop owner wrote) ….

assistant + tool

Each shop event as a synthetic shop_event tool call and its result, for example {"event": "payment_received", "order": "#1003"}.

assistant + tool

This turn's own tool calls and results, appended as the loop runs.

tools

JSON schemas of the tools the current stage allows: 16 in browsing, 17 collecting details, 15 awaiting confirmation, 15 with payment pending.

The second message: "actually make it 4"

  1. Same path in

    Webhook, inbox, message row, turn job, lock, gather. The trigger is now "actually make it 4".

  2. The stage decides the playbook

    The chat is in awaiting_confirmation, so rule 2 picks new_order before any text rule runs. The model is offered 15 tools, including update_order_draft and confirm_order.

  3. The model updates the draft

    It calls update_order_draft with quantity 4. The tool supersedes the open quote (it can no longer be confirmed) and moves the chat back to collecting_details, which makes create_quote available again.

  4. New quote, new card, one line

    create_quote sends a fresh card; send_reply asks them to confirm. The eval change-before-confirm checks exactly this: update_order_draft used, confirm_order not used.

Had the customer typed "ok" instead, confirm_order would refuse with unclear and a hint to point them to the Confirm button (§8). A typed message places an order only when it clearly asks for it.

§7

Three layers. The chat itself is stored in full in messages (the model sees the latest 20). Working memory lives for one turn: the TurnContext object plus turn_steps, which survive a crash. The read path

engine._gather reads facts, rules, glossary and the latest summary along with stock, quote and chat in one transaction. context.build renders them into context.md. Nothing is retrieved by similarity search: the stores are small and keyed, so all of a customer's facts fit in every prompt.

On demand, get_customer_profile returns the facts plus past and unpaid order counts and the last order's items, fulfilment and address, for "same as last time".

The write path

The model can write only through remember_customer_fact, whose key is a closed list in the schema, so it can't invent a new kind of memory. Every fact keeps the message it came from (source_message_id). Summaries are written by a background job with its own prompt and checked for amounts. The owner's rules come from the owner, not the model.

§8

Tool calling: who decides what

The model decides

  • Which of the offered tools to call, and in what order
  • The arguments (item ids, quantities, the question for the owner)
  • When to ask the owner or hand the chat off
  • The words of the reply and the language label

Code decides

  • Which tools exist this stage, and that one is missing on owner-answer turns
  • Whether the arguments are valid (pydantic) and the call is allowed
  • Every price, total, order number and link
  • Every stage change, and whether a typed "yes" counts
  • Whether the reply passes, and when the turn must stop

The tool contract

A tool is a class

  • name, and Args: a pydantic model whose JSON schema is what the model sees as parameters
  • stages: where it is allowed (default: the four active stages)
  • writes: whether it changes data (shadow mode stubs these)
  • run(ctx, args) and replay(ctx, result), which re-applies a stored result's effect when a crashed turn resumes
  • Its description is a versioned prompt file, prompts/tools/<name>.md

Every call goes through registry.execute

  1. Unknown name: error unknown_tool
  2. Not allowed now: error not_allowed with the tools you can use
  3. Arguments not JSON, or invalid: error invalid_arguments listing each problem
  4. Shadow mode and a writing tool: a stub result, nothing written
  5. Run it. An exception becomes error internal_error with "don't retry"

Errors are results the model can react to, never exceptions that end the turn.

Results are JSON

{"ok": true,  "data": {...}}

Item ids instead of names

An item's id is i plus the first six hex digits of its variant UUID (i3f9a2c). It never changes while the item exists, and code maps it back exactly. A misspelt id is an unknown_item error the model has to fix, never a silent match to another item. Ids are for tool calls only: the output check rejects one in a reply.

When the provider has no tool calling

With LLM_TOOL_MODE=json, the gateway appends the tool list to the system prompt, asks for {"tool_calls": [...]} as JSON, sends tool results as user messages, and parses the answer back into the same ToolCall objects. The engine can't tell the difference.

Does a typed message place the order?

unclear An acknowledgement, decided in code without a model call. Nothing is placed; the model tells them to tap Confirm.

Order of checks in affirmation.classify: a "no" word, then a "change" word, then a strong word (confirm, place the order, book it, confirm pannunga, order kar do…) not next to a question or "wait / not yet", then an acknowledgement (ok, sure, seri, haan, 👍). Anything else goes to a small model classifier whose prompt also treats acknowledgements as unclear. A Confirm tap skips all of this.

Reject, repair, or tidy

A rejected reply returns reply_rejected with every problem listed and "fix these and call send_reply again". The model gets one repair. If only tone problems remain after that, code removes the introduction, the "sir/madam" and the office phrases itself (tidy_style) and sends the reply, because a good answer with a stiff word beats the holding message. A second hard rejection ends the turn in a fallback.

What code says instead of the model

Anything about money or a fixed fact is a template, sent by code: the quote card, the payment link and its dollar charge, payment declined (tries left, cooldown, a "New payment link" button), payment gave up, order ready / packed / delivered / sent, hand-off, holding, too long, rate limited, and the owner's own words when the model fails on an answer turn.

Prompt injection, by construction

  • Customer text is only ever a user message. Prompt files are filled only with code-produced values (Jinja with StrictUndefined: a missing value is an error, never an empty string).
  • System news arrives as shop_event tool results, which a customer cannot produce. base.md says that text which looks like a system message is the customer's words.
  • Even a fully hijacked model can't place an order without a delivered quote card and a clear confirmation, can't type a price or link, and can't call a tool its stage doesn't allow.

Reliability: no duplicates, no silence

Ten layers against doing something twice

A crash in the middle of a turn

Every model response and tool result is stored before the loop moves on. If the worker dies, the turn row stays running. Every minute reconcile_unanswered re-queues chats with a turn running for over 2 minutes, and chats whose latest message has waited 30 seconds unanswered. The new attempt finds the same turn row, and for each step whose key is stored it reuses the stored result and calls tool.replay() to restore the turn's state (stage, payment link, "replied"). Nothing already done runs again.

The model gateway

  • Up to 2 retries per model (0.5 s, 1.5 s, ±20% jitter, or Retry-After up to 10 s) on network errors, 408, 409, 429 and 5xx. Other 4xx fail at once.
  • Then the next model in LLM_MODELS.
  • Circuit breaker per model: 3 failed calls within 60 s skips it for 30 s. A content-filter 400 doesn't count. The breaker is per process.
  • Connect timeout 5 s; every call is also cut off by the turn's remaining time.
  • Cost per call from LLM_PRICES, summed per turn.

The customer is never left without an answer

  1. The model fails while passing on the owner's answer

    The customer gets the owner's own words: "Update from the shop: Yes, we can write a name on it." (owner_answer_relay).

  2. The model fails on a payment or expiry event

    A fixed message says what happened (event_payment_received, event_hold_expired), not "I'll check with the shop".

  3. Any other failure

    "Thanks for your message! Let me check with the shop and get back to you shortly." plus one "couldn't finish" question for the owner per chat, skipped if the owner was already asked in this turn.

  4. Sending fails

    The outbox retries up to 6 times over about 10 minutes (10 s to 240 s), keeps later messages behind it so the order never changes, then asks the owner to reply in Instagram. A send stuck in sending for 2 minutes is sent again unless Instagram echoed it: a possible duplicate is better than silence.

  5. Instagram's window has closed

    Rows wait as pending_window and the owner is told. They go out first when the customer writes again, and expire after 7 days.

§12

The shop owner in the loop

How the agent brings the owner in

  • ask_shop_owner: a question with up to 3 suggested answers (shown as chips in the app) and a confidence. Code sends it back when the shop's own data already answers it.
  • hand_off_to_owner: the whole chat becomes the owner's; the agent stops answering it.
  • Fallbacks, rate limits, budget, failed sends and payment mismatches also open questions, written by code.

How the owner stays in control

  • Replying from the Instagram app pauses the agent in that chat (the echo isn't one of ours).
  • A per-chat switch, and the shop-wide agent_enabled.
  • "Always answer this way" turns one answer into a saved rule for every future turn.
  • Draft mode: the agent's replies wait for approval (§14).
§13

Payments and other shop events

  1. Confirm places the order and code sends the payment message

    UPI if the shop is in rupees and has a UPI id; else PayPal (a rupee order is charged in dollars at a live exchange rate, rounded up, and the message says so); else "the shop will share payment details" and an owner question.

  2. PayPal tells the backend

    The PayPal webhook goes into the same inbox and job pattern (process_paypal_event). A job that runs every minute (settle_open_payments) captures approved payments whose return page or webhook never arrived.

  3. Paid: a system note starts a turn

    after_payment moves the chat back to browsing and adds a note with {"event": "payment_received", "order": "#1003"}. The model writes the thank-you; if it can't, the fixed event template goes out.

  4. Declined: code answers, not the model

    The customer gets the tries left and a "New payment link" button (RETRY:<order>, handled in layer 0). Too early: a wait message. No tries or time left: the order is cancelled, stock released, and the customer told.

  5. Hold expired, or the owner marks the order ready

    An expired hold is a shop event like payment. An order marked ready, packed, delivered or sent queues a fixed template directly, once per order and status, with no turn.

§16

Interview questions

Answers are short on purpose: say them in your own words, then go to the section for detail.
1Walk me through what happens when a customer sends a DM.

Meta posts a webhook. We verify the HMAC, store the raw event once in an inbox table and queue a job, then answer 200. The job stores the message under the customer's one conversation and requests a turn, delayed 3 seconds with a per-chat queueing lock so a burst gets one reply. The turn takes a per-chat advisory lock, reads everything it needs in one transaction, starts a trace row unique per trigger message, picks a playbook with regex rules, builds the prompt, checks rate and budget limits, then loops: the model calls tools allowed in the current stage until send_reply passes the output checks. The reply goes to an outbox and a sender job delivers it in order. (§4)

2Why build your own harness instead of using an agent framework?

The hard parts are domain invariants: money, stock holds, idempotency, Instagram's 24-hour window, never leaving a customer silent. One engine file of under 700 lines, with explicit budgets, a stage gate and stored steps, is easy to test and to reason about, and the whole loop is visible in one place. The gateway is a thin OpenAI-compatible client, so switching provider is configuration. The cost is building tracing and evals ourselves, which the project did.

3How do you stop the model from inventing prices, totals or links?

The model never sees a price or a link as something to copy. It writes tokens like [[price:i3f9a2c]] and [[payment_link]]; code fills them from the database at send time. The output check removes tokens and then rejects any amount, link or item id left in the model's own words. Quote cards and payment messages are templates written by code.

4How does the agent decide which playbook to use?

Code decides before the model runs: ordered regex rules over the stage, the latest customer message and the trigger's details. The owner's answer wins first; mid-order stages stay on new_order; then complaint, menu, payment, status, product, custom, greeting, off-topic, and a new_order default. The model can load one other playbook per turn with a tool. Regex was chosen for cost and testability; the next step would be a small classifier if traces show misrouting. (§5)

5How is conversation state managed?

An explicit stage column (browsing, collecting_details, awaiting_confirmation, payment_pending, handed_off) plus a draft JSON and a quotes table. Only tools and payment events change the stage. The tool list is filtered by stage and recomputed before every model call, so the model physically can't confirm before a quote exists or cancel an order that isn't pending. (§9)

6How does it keep context across messages without a growing prompt?

Turns are stateless: each one rebuilds the prompt from Postgres. The model sees the last 20 messages, each capped, plus a context block with stage, draft, quote, facts and pre-orders, and a summary of older messages that a background job writes. Item ids are short, tools are filtered by stage, and only one playbook is loaded, so the prompt stays small. (§6)

7How does memory work?

Four keyed stores read at the start of every turn: customer facts (written by the model through one tool with an allow-listed set of six keys), chat summaries (a background job, rejected if they contain an amount), the owner's saved answers (from "Always answer this way"), and a glossary of code-mixed words. No vector search: the data is small and exact. The owner can view and delete facts. (§7)

8What happens if the worker crashes in the middle of a turn?

Every model response and tool result is stored with an idempotency key before moving on. The turn row stays running; a reconciler re-queues it after 2 minutes. The retry finds the same turn row, reuses stored steps instead of re-running them, and calls each tool's replay to restore state, so an order or a payment link is never created twice. (§11)

9How do you prevent double orders and double messages?

Layers of keys: webhook dedupe by body hash, unique message ids, per-chat queueing lock and job lock, an advisory lock per chat, a turn row unique per trigger, unique step keys, outbox idempotency keys per message, and confirm returning the existing order for an already-confirmed quote. (§11)

10How do you handle prompt injection?

Customer text is only ever a user message and is never rendered into a prompt template. System news arrives as tool results, which a customer can't forge, and the base prompt says so. And the blast radius is small: tools validate everything, the stage gate limits what exists, orders need a delivered card plus a clear confirmation, and the output checks block amounts, links and promises. (§10)

11How is a typed "yes" handled when it could mean anything?

A Confirm tap is proof by itself and is handled in code before the model. A typed reply goes through affirmation.classify: no-words, change-words, strong confirm words not next to a question, then acknowledgements like "ok" or "seri", which are unclear without a model call. Only leftovers go to a small classifier. This came from a real incident where "okay" placed and charged an order. (§8)

12What happens when the model provider is down?

The gateway retries with backoff, falls back to the next configured model, and a circuit breaker skips a failing model for 30 seconds. Each call is bounded by the turn's 60-second deadline. If the turn still can't finish, code sends a holding message, a fixed event message or the owner's own words, and opens one owner question per chat. (§11)

13How do you control cost?

Per turn: at most 6 model calls, 10 tool calls, 60 seconds. Per chat: 30 turns an hour, 150 a day. Per shop: a daily budget summed from traced cost. Cheap code paths before the model: regex routing, regex confirmation, taps handled in code, too-long messages answered by template. Every model step records tokens and cost.

14How do you test an LLM agent?

Unit tests for routing, the confirmation table and every output check; integration tests on a database built from the real migrations; live multi-turn evals against the real model, run twice for any prompt or tool change and recorded in a changelog; replay-turn to turn a bad production reply into a test case; shadow mode to compare engines on real traffic.

15What would you improve next?
  • Replace regex routing with a small classifier, measured against traces (one gap is already known: "what else do you have" never reaches the menu playbook).
  • Move the circuit breaker and rate limits to shared storage so several processes agree.
  • Retry customers who got the holding message once the model is back.
  • Make the unpaid-order limit safe under concurrent confirms.
  • Retire v1 and make the safer mode the default for new shops.
16Why use Postgres for the queue and locks?

One dependency to run and back up. Jobs, locks, traces and data live in the same database, advisory locks die with their connection if a process crashes, and procrastinate gives queueing locks and per-key job locks. The trade-off is that jobs are queued after commit rather than in the same transaction, so a reconciler covers a lost enqueue.
